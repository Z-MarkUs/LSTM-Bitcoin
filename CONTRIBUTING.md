# Contributing

Thank you for improving LSTM Bitcoin Research. This repository is an engineering and
research demonstration, not a trading system. Contributions should make the evidence
more reproducible, easier to audit, or more honest about its limits.

## Development setup

Install [uv](https://docs.astral.sh/uv/) and a supported Python version, then create the
locked development environment:

```bash
uv sync --locked --all-extras
```

The project supports Python 3.11 and 3.12. Do not update a dependency in
`pyproject.toml` without committing the matching `uv.lock` change.

## Local quality gate

Run the same checks used by continuous integration before opening a pull request:

```bash
uv run --frozen ruff check src tests scripts notebooks
uv run --frozen ruff format --check src tests scripts notebooks
uv run --frozen mypy src/lstm_bitcoin
uv run --frozen pytest -m "not network" --cov=lstm_bitcoin --cov-branch --cov-report=term-missing --cov-fail-under=90
uv run --frozen pip-audit --skip-editable
uv run --frozen bandit -q -r src/lstm_bitcoin
uv build --no-sources
```

Tests must be deterministic and offline unless they carry the declared `network`
marker. Unit tests should use the deterministic fixture builders in
`tests/conftest.py`, not download market data.

## Research rules

- Keep every split chronological. Random train/test splits are not acceptable for the
  reference time-series experiment.
- Fit scalers, imputers, feature selection, and model-selection logic only on the
  training portion of each fold.
- A feature may be used only if its point-in-time availability is documented. Do not
  infer availability from the date printed in a revised dataset.
- Never use outer-test performance to select hyperparameters, thresholds, features,
  or seeds.
- Compare the LSTM with the documented naive and linear baselines using identical
  dates and input windows.
- Do not make profitability, accuracy, or production-readiness claims that are not
  supported by checked-in artifacts.
- Describe trading output as an illustrative signal simulation. Preserve its execution
  lag, turnover costs, and stated limitations.

## Updating the reference evaluation

Ordinary code changes should not rewrite `evaluation/results/reference-v1`. Update the
reference result only when the data manifest, methodology, model, or declared metric
definition intentionally changes.

Before accepting an update:

1. Explain the methodological reason in the pull request and `CHANGELOG.md`.
2. Lock the configuration before inspecting the outer-test result.
3. Reproduce the run from `configs/reference.toml` in a clean, locked environment.
4. Verify the run manifest and checksums.
5. Review every changed metric, fold boundary, prediction, assumption, and chart.
6. State whether the LSTM beat each baseline; a negative result is valid and must not
   be hidden.

```bash
uv run --frozen lstm-bitcoin reproduce \
  --config configs/reference.toml \
  --output evaluation/results/reference-v1 \
  --plots docs/assets \
  --force
uv run --frozen lstm-bitcoin verify \
  --run evaluation/results/reference-v1
```

## Dependency updates and historical evidence

Dependency-only updates preserve the published reference bundle. CI reproduces the
experiment from the PR's clean, locked environment and compares all metrics,
folds, predictions, training rows, signal outputs, and input declarations with the
published reference, using the existing numeric tolerances. The required evidence
integrity job depends on that reproduction succeeding. Changed dependency versions
are recorded in the fresh run manifest and printed in the comparison log; the old
manifest continues to describe the original run. CI uploads the new evidence.

Source, data, configuration, and non-dependency project settings must still match
the recorded revision. A dependency update that changes the results beyond the
existing tolerances fails and needs explicit investigation, not a rewritten baseline.

## Pull requests

Keep changes focused and include:

- the question or defect being addressed;
- tests for the changed behavior, including failure paths;
- commands used to validate the change;
- data, metric, or presentation implications;
- any remaining limitation or unverified assumption.

Do not commit credentials, downloaded caches, virtual environments, model weights,
notebook checkpoints, IDE state, or generated bytecode. Do not add executable serialized
models such as pickle files.
